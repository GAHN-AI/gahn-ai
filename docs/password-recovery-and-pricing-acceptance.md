# GAHN AI — Email / Google password setup and recovery

## Intended sign-in behavior

- A learner's **email address** is the sign-in identifier, not a separate username. The email/password login already exists.
- Google login works independently. A Google-authenticated account may add email/password authentication using Supabase `updateUser({ password })` after authorized account access. Doing so does **not** require the learner to register a second account or stop using Google.
- If someone registered via email and password and later uses Google **with the exact same verified email**, Supabase can automatically link these identities. A different email is a separate account until properly linked.
- The `Forgot password / create one` control on Login, and the password setup/reset link in Settings, both call `resetPasswordForEmail`. Requests are deliberately not allowed to reveal whether a particular email has an account.
- The link is intended to reach `/auth/callback?next=/update-password`, exchange a valid recovery code or verify a recovery token, then show `/update-password`. After a successful update the existing page signs the user out locally and points to Login.
- Never create a public `username -> email` lookup endpoint or store passwords in a profile record. Supabase Auth securely manages password verification.

## Source-level fix — October 2026

The login and signup clients previously used a configured `NEXT_PUBLIC_SITE_URL` for OAuth and email redirects, whereas Settings sent a reset link to `window.location.origin`. The auth callback then always redirected through `SITE_URL`. This could switch between `gahnai.com` and `www.gahnai.com`, or between a preview domain and production, breaking the cookie-bound PKCE flow.

Login and signup now start OAuth/confirmation and recovery on **the current origin**, matching Settings. The callback redirects only on a trusted request origin: the production apex/www hosts, the exact current Vercel deployment hostname, or local development. Unknown hosts fall back to the configured site URL to avoid host-based open redirects.

The callback handles recovery links by sending verified sessions to the password form rather than the dashboard. This is a code fix, **not proof that the email link is configured correctly in the hosted Supabase project**.

## Supabase dashboard checks (may be necessary to fix landing-page redirects)

The connected Supabase project tools do not currently expose Auth URL Configuration or Email Template editing, so these settings require a manual check. Navigate to **Supabase Dashboard → Authentication → URL Configuration**, and confirm:

1. **Site URL** uses the actual canonical production hostname (either `https://www.gahnai.com` or `https://gahnai.com`, depending on the configured Vercel domain redirect).
2. **Redirect URLs** allow the exact URLs generated by the application, including:
   - `https://www.gahnai.com/auth/callback`
   - `https://www.gahnai.com/auth/callback?next=/update-password`
   - `https://gahnai.com/auth/callback`
   - `https://gahnai.com/auth/callback?next=/update-password`
   - Corresponding OAuth callback URLs with `?intent=login` and `?intent=signup` (or a documented suitable allowlist wildcard).
3. Any Vercel preview URL used for sign-in is on the allowlist if testing OAuth/recovery on preview deployments.
4. At **Authentication → Email Templates → Reset password**, check that the link actually uses Supabase's `{{ .ConfirmationURL }}` (or a correctly constructed PKCE/token-hash recovery link honoring `{{ .RedirectTo }}`). A template hardcoded to `{{ .SiteURL }}` will send the user to the homepage even when the code passes a callback URL.
5. Do not share a working password-reset URL or token with anyone. Reset links are short-lived, single-use credentials.

## Acceptance tests (must still be completed with real test accounts)

1. Create a new **email/password** test account, verify the email, and confirm login with the email and original password.
2. While signed in, click **Settings → Email password setup / reset link**. Click the newly sent email's link in the **same browser** that requested it. It should show `/update-password`, not the landing page.
3. Enter and confirm a strong new password. Verify the account signs out and a normal login using the new password works; the original password should stop working.
4. Test the `Forgot password / create one` flow from Login while signed out, with the same recovery behavior.
5. Create a Google-only test account using a verified email. Confirm Google sign-in. Request password setup and set a new password via a verified email link (or use authenticated `updateUser` if the provider configuration does not email OAuth-only accounts). Confirm the **same Supabase user ID** and profile are retained.
6. Confirm the Google user can subsequently log in using **email + new password**, *and* can still log in using Google; verify there is no duplicate profile.
7. Test the recovery link expired/used twice (should produce a helpful error, not log in), email delivery rate limits, and the apex/www hostname paths.
8. Verify links sent from the production app, including Vercel canonical-domain behavior. Test previews only with appropriately allowed URLs.
9. Confirm no free text lessons, paid checkout, or video usage were reactivated. This change concerns authentication and clear future pricing only.
10. Confirm the eventual pricing page publishes **monthly tutor minutes, maximum session duration and any overage policy** before any checkout is opened; today's figures remain to-be-announced.

**Important:** Supabase PKCE codes may require opening the emailed link in the same browser/device where the recovery request was initiated. A secure token-hash email template can support a separate verified handoff if implemented and validated properly.

A green build does not prove that a real reset email works: manual end-to-end testing and Supabase URL/template verification remain necessary.
